# 이음 — 서비스 분리본 매니페스트 (eum-services-k8s)

4~5부에서 쓰는 매니페스트입니다. `../eum-services/` 의 네 서비스를 클러스터에 올립니다.

3부의 `../eum-k8s/` 는 한 덩어리를 올렸습니다. 여기서는 넷입니다. 파일 수가 어떻게
늘어나는지 보시라고 손으로 다 적어 두었습니다. 그 반복을 헬름으로 줄이는 것이
`../eum-helm/` 이고, 본문 20.1 입니다.

| | 3부 (한 덩어리) | 4~5부 (넷으로 나눈 뒤) |
| --- | --- | --- |
| 매니페스트 파일 | 11장 | 31장 |
| 렌더된 오브젝트 | 14개 | 33개 |

셋으로 나눈 데이터베이스와 브로커가 더해진 몫이 있고, 나머지는 서비스마다 같은 형태를
다시 적은 몫입니다.

## 구조

```
base/
  namespace.yaml           네임스페이스
  configmap-common.yaml    네 서비스가 함께 쓰는 값
  secret.yaml              계정과 열쇠 (실습용)
  ingress.yaml             /api → 게이트웨이, / → 화면
  core/                    본체     — 배포·서비스·컨피그맵·PVC·HPA·PDB
  notification/            알림     — 배포·서비스·컨피그맵·HPA·PDB
  payment/                 지급     — 배포·서비스·컨피그맵·HPA·PDB·크론잡
  gateway/                 게이트웨이 — 배포·서비스·컨피그맵·HPA·PDB
  web/                     화면     — 배포·서비스·PDB
db/mysql.yaml              실습용 MySQL (데이터베이스 셋 + 계정 셋)
broker/rabbitmq.yaml       실습용 RabbitMQ
overlays/local/            노트북 kind 클러스터용 차이
```

배포·서비스·컨피그맵·HPA·PDB 다섯 장이 서비스마다 있습니다. 이름만 다르고 형태는
거의 같습니다. 서비스를 하나 더 나누면 다섯 장을 또 만들어야 합니다.

## 돌려 보기

```bash
# 렌더해서 눈으로 확인
kubectl kustomize overlays/local

# 올리기
kubectl apply -k overlays/local
```

DB 와 브로커가 먼저 떠야 합니다. 오버레이에 함께 들어 있어 한 번에 올라가지만, 서비스
파드는 그 둘이 준비될 때까지 재시작을 되풀이합니다. 정상입니다.

## 3부와 달라진 것

**계정이 서비스마다 다릅니다.** `eum_app` 하나가 아니라 `eum_app`·`noti_app`·`pay_app`
셋입니다. 각 계정은 자기 데이터베이스에만 권한이 있습니다. 알림이 신청서를 읽으려 하면
문법 오류가 아니라 권한 오류로 막힙니다. 경계를 코드에만 두지 않고 데이터에도 세운
것입니다(13.2).

표준프레임워크 MSA 템플릿은 여기까지 가지 않습니다. 여섯 서비스가 계정 하나를 나눠 쓰고
그 계정에 모든 데이터베이스 전권이 있습니다. 그러면 급할 때 옆 서비스 표를 직접 읽는
코드가 들어가고, 막을 방법이 없습니다.

**브로커가 생겼습니다.** 서비스끼리 동기 호출로만 이으면 알림이 느릴 때 접수가 같이
느려집니다. RabbitMQ 를 두고 이벤트로 잇습니다(15장). 브로커를 카프카로 바꾸는 이야기는
부록 F 에 있습니다.

**들어오는 문이 게이트웨이 하나입니다.** 인그레스에 서비스별 경로를 늘어놓지 않습니다.
그러면 서비스가 늘 때마다 인그레스를 고쳐야 하고, 토큰을 검증할 곳이 사라집니다(16.1).

**야간 배치가 크론잡입니다.** 앱 안의 `@Scheduled` 를 그대로 두면 파드를 늘린 만큼 같은
배치가 겹쳐 돕니다. 지급은 겹치면 이중 이체입니다(11.5).

## 노트북에서 돌릴 때 달라지는 것

`overlays/local/` 이 관리형 클러스터 기준값에서 무엇을 바꾸는지 밝혀 둔 곳입니다.

- 서비스마다 벌 수를 줄입니다. 노트북 한 대에 파드 다섯 종류를 여러 벌씩 띄울 수 없습니다.
- 본체만 자동 확장을 켜고 나머지 셋의 HPA 는 지웁니다. 벌이 하나뿐이면 늘릴 자리가 없습니다.
- 벌이 하나인 서비스의 PDB 를 0 으로 둡니다. 그대로 두면 노드를 비울 때 막힙니다.
- 첨부 볼륨을 `ReadWriteOnce` 로 낮춥니다. kind 기본 스토리지는 `ReadWriteMany` 를 주지
  않습니다. 파드를 늘렸을 때 첨부 파일이 어떻게 갈리는지 10.3 에서 이 차이로 확인합니다.

**본체의 `replicas` 는 지웁니다.** 자동 확장을 켠 배포에 `replicas` 를 같이 적어 두면
둘이 서로 값을 되돌려 파드 수가 오르내립니다.

## 이미지

매니페스트가 가리키는 이미지는 이 이름들입니다.

| 이미지 | 만드는 곳 |
| --- | --- |
| `eum/eum-core:1.0.0` | `../eum-services/eum-core` |
| `eum/eum-notification:1.0.0` | `../eum-services/eum-notification` |
| `eum/eum-payment:1.0.0` | `../eum-services/eum-payment` |
| `eum/eum-gateway:1.0.0` | `../eum-services/eum-gateway` |
| `eum/eum-web:1.0.0` | `../eum-mono/frontend` 를 빌드해 nginx 에 담은 것 |

폐쇄망에서는 이 이름 앞에 반입 절차를 거친 사내 레지스트리를 붙입니다(20.3).
