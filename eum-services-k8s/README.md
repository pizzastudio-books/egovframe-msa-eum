# 이음 — 서비스 분리본 매니페스트 (eum-services-k8s)

이 매니페스트는 4부와 5부에서 사용합니다. `../eum-services/` 디렉터리에 있는 네 서비스를 쿠버네티스 클러스터에 띄웁니다.

3부의 `../eum-k8s/` 는 한 덩어리를 올렸습니다. 여기서는 넷입니다. 파일 수가 어떻게
늘어나는지 보시라고 손으로 다 적어 두었습니다. 그 반복을 헬름으로 줄이는 것이
`../eum-helm/` 이고, 본문 20.1 입니다.

| | 3부 (한 덩어리) | 4~5부 (넷으로 나눈 뒤) |
| --- | --- | --- |
| 매니페스트 파일 | 11장 | 31장 |
| 렌더된 오브젝트 | 14개 | 33개 |

데이터베이스와 브로커는 셋으로 나누었고, 이로 인해 구성이 달라진 부분이 있습니다. 나머지 부분은 서비스마다 동일한 형태를 반복하여 작성했습니다.

## 구조

```
base/
  namespace.yaml           네임스페이스
  configmap-common.yaml    네 서비스가 함께 쓰는 값
  secret.yaml              계정과 열쇠 (실습용)
  ingress.yaml             /api → 게이트웨이, / → 화면
  core/                    본체     — 배포·서비스·컨피그맵·PVC·HPA·PDB
  notification/            알림     — 배포·서비스·컨피그맵·HPA·PDB
  payment/                 지급     — 배포·서비스·컨피그맵·HPA·PDB·크론잡
  gateway/                 게이트웨이 — 배포·서비스·컨피그맵·HPA·PDB
  web/                     화면     — 배포·서비스·PDB
db/mysql.yaml              실습용 MySQL (데이터베이스 셋 + 계정 셋)
broker/rabbitmq.yaml       실습용 RabbitMQ
overlays/local/            노트북 kind 클러스터용 차이
```

배포·서비스·컨피그맵·HPA·PDB 다섯 장이 서비스마다 있습니다. 이름만 다르고 형태는
거의 같습니다. 서비스를 하나 더 나누면 다섯 장을 또 만들어야 합니다.

## 돌려 보기

```bash
# 렌더해서 눈으로 확인
kubectl kustomize overlays/local

# 올리기
kubectl apply -k overlays/local
```

DB와 브로커가 먼저 실행되어야 합니다. 이 둘은 오버레이에 함께 포함되어 한 번에 배포되지만, 서비스 파드는 DB와 브로커가 준비될 때까지 재시작을 반복합니다. 이 동작은 정상입니다.

## 3부와 달라진 것

**계정이 서비스마다 다릅니다.** `eum_app` 계정 하나가 아니라 `eum_app`, `noti_app`, `pay_app` 계정 세 개를 사용합니다. 각 계정은 자신이 담당하는 데이터베이스에만 접근 권한을 가집니다. 예를 들어 알림 서비스가 신청서 데이터를 읽으려 하면 문법 오류가 아니라 권한 오류로 거부됩니다. 이는 경계를 코드 수준에서만 설정하지 않고, 데이터베이스 단계에서도 명확히 구분한 것입니다(13.2).

표준프레임워크 MSA 템플릿은 이 단계까지 적용하지 않습니다. 여섯 개의 서비스가 하나의 계정을 공유하며, 해당 계정에 모든 데이터베이스에 대한 전권이 부여됩니다. 이 경우 긴급 상황에서 다른 서비스의 테이블을 직접 조회하는 코드가 삽입될 수 있으며, 이를 막을 기술적 제어 수단이 없습니다.

**브로커가 생겼습니다.** 서비스끼리 동기 호출만으로 연결하면 알림 처리가 느려질 때 신청 접수도 함께 느려질 수 있습니다. 이 문제를 해결하기 위해 RabbitMQ 를 도입하고, 서비스 간 연결을 이벤트 기반으로 바꾸었습니다(15장). 브로커를 Kafka 로 교체하는 방법은 부록 F 에 설명되어 있습니다.

**들어오는 요청은 게이트웨이 하나를 통해 처리합니다.** 인그레스에 서비스별 경로를 나열하지 않습니다.  
서비스가 늘어날 때마다 인그레스 매니페스트를 수정해야 하며, 토큰 검증 로직을 담을 곳도 사라지기 때문입니다(16.1).

**야간 배치는 크론잡으로 구현합니다.** 앱 내부의 `@Scheduled` 어노테이션을 그대로 유지하면, 파드 수에 비례해 같은 배치가 중복 실행됩니다. 지급 작업의 경우, 이처럼 중복 실행되면 이중 이체가 발생할 수 있습니다(11.5).

## 노트북에서 돌릴 때 달라지는 것

`overlays/local/` 디렉터리는 관리형 클러스터의 기준값을 어떤 식으로 덮어쓰는지 명시한 곳입니다.

- 서비스마다 레플리카 수를 줄입니다. 노트북 한 대에 파드 다섯 종류를 여러 개씩 띄울 수 없습니다.
- 본체만 자동 확장을 켜고 나머지 셋의 HPA 는 지웁니다. 레플리카가 하나뿐이면 늘릴 자리가 없습니다.
- 레플리카가 하나인 서비스의 PDB 를 0 으로 둡니다. 그대로 두면 노드를 비울 때 막힙니다.
- 첨부 볼륨을 `ReadWriteOnce` 로 낮춥니다. kind 기본 스토리지는 `ReadWriteMany` 를 주지
파드를 늘렸을 때 첨부 파일이 어떻게 분배되는지 확인하려면, 10.3에서 두 방식의 차이를 정리한 표를 참조합니다.

**본체의 `replicas`는 삭제합니다.** 자동 확장을 활성화한 배포에 `replicas`를 명시하면, 자동 확장 기능과 수동 설정 값이 충돌하여 파드 수가 예측 없이 오르내릴 수 있습니다.
