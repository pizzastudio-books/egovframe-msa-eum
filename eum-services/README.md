# 이음 — 서비스 분리본 (eum-services)

4~5부에서 사용하는 스냅숏입니다. 이음은 한 덩어리였던 것을 네 개로 나누었습니다.

| 모듈 | 담당 | 갈라져 나온 곳 |
| --- | --- | --- |
| `eum-gateway` | 토큰 검증 · 권한 전파 · 감사 로그 | 16장 |
| `eum-core` | 회원 · 공통 · 지원사업 · 신청 · 심사 | 본체로 남은 것 |
| `eum-notification` | 문자 · 메일 발송 | **첫 분리(15장)** |
| `eum-payment` | 지급 지시 · 이체 연계 · 야간 배치 | 17장, 사가는 18장 |
| `eum-contract` | 서비스 사이에 오가는 이벤트 규격 | — |

## 데이터베이스도 나뉘어 있습니다

| 서비스 | 데이터베이스 | 계정 | 인스턴스 |
| --- | --- | --- | --- |
| eum-core | `eum` | `eum_app` | 공용 |
| eum-notification | `eum_noti` | `noti_app` | 공용 |
| eum-payment | `eum_pay` | `pay_app` | **전용** |

계정 권한이 자기 데이터베이스로 제한되어 있어, 알림 서비스가 신청서를 조회하려 할 때 문법 오류가 아니라 **권한 오류**로 차단됩니다. 경계는 코드에만 존재하는 것이 아니라 데이터에도 적용됩니다.

표준프레임워크 MSA 템플릿은 이 단계까지 진행하지 않습니다. 여섯 서비스가 하나의 계정을 공유하며, 해당 계정에 모든 데이터베이스의 관리 권한이 부여됩니다. 이 차이는 13.2에서 설명합니다.

## 흐름

```
[본체]  심사 승인 저장 + 아웃박스 기록          ← 한 트랜잭션. 여기까지는 ACID
          │
        발송기가 아웃박스를 읽어 브로커로 발행
          │
[지급]  선정됨 수신 → 지급 지시 생성 → 야간에 금융망 이체
          │
     ┌────┴────┐
   성공        실패
     │          │
[본체]  지급완료됨 수신          지급실패됨 수신
      신청을 지급완료로           신청을 접수로 되돌림 (보상)
```

**아웃박스가 왜 필요한가.** 템플릿은 저장 직후 곧바로 발행됩니다. 그런데 저장은 성공했으나 발행 전에 프로세스가 종료되면, 해당 이벤트는 유실될 수 있습니다. 아웃박스는 이벤트를 업무 자료와 동일한 트랜잭션으로 기록하여, 이 유실 구간을 막습니다(18.1·18.2).

**멱등이 왜 필요한가.** 브로커는 메시지를 한 번 이상 전달할 수 있지만, 정확히 한 번만 전달한다는 보장을 하지 않습니다. 아웃박스 발송기도 전송에 실패하면 동일한 메시지를 다시 보냅니다. 따라서 수신 쪽에서는 같은 메시지가 여러 차례 도착하더라도 최종 결과가 달라지지 않아야 합니다. 알림과 지급 서비스는 `event_id` 를 기록해 중복 메시지를 식별하고, 본체에서 상태를 확인한 후 중복을 걸러 냅니다(18.4).

**브로커를 아는 코드는 어디인가.** 아웃박스 발송기와 리스너 어댑터 두 곳입니다.  
업무 코드는 아웃박스에 메시지를 적기만 하면 됩니다. RabbitMQ 를 카프카로 바꾸더라도 수정이 필요한 곳은 이 두 곳으로 한정됩니다(부록 F).

## 돌려 보기

```bash
./gradlew build          # 시험 84건
./gradlew :eum-core:bootRun          # 8080
./gradlew :eum-notification:bootRun  # 8081
./gradlew :eum-payment:bootRun       # 8082
./gradlew :eum-gateway:bootRun       # 8000
```

브로커와 데이터베이스는 `../local/` 디렉터리에 있습니다. 실습은 해당 디렉터리 내 안내를 따릅니다.

## 브로커 없이 검증합니다

시험에서는 RabbitMQ 를 띄우지 않습니다. Spring Cloud Stream 의 시험 바인더가 큐를 사용하지 않고 메시지를 직접 넣고 빼기 때문입니다. 따라서 `./gradlew build` 명령 하나로 리스너, 멱등, 아웃박스, 보상 기능을 모두 확인할 수 있습니다.

브로커를 실제로 띄워 시스템에 연결하는 작업은 별도의 확인 절차입니다. 이 절차는 `../local/` 디렉터리에 있습니다.

## 게이트웨이를 MVC 로 만든 이유

Spring Cloud Gateway는 기본적으로 리액티브 방식을 사용하지만, `spring-cloud-starter-gateway-server-webmvc` 의존성을 추가하면 서블릿 기반으로 실행할 수 있습니다. 이 책에서는 리액티브 방식을 채택하지 않기로 결정하였고, 이에 따라 서블릿 기반 실행도 예외로 두지 않았습니다. 이 판단 근거는 16.2에 정리되어 있습니다.

게이트웨이는 **토큰 검증·권한 전파·감사 로그**를 담당합니다. 경로 분배와 TLS 종단은 인그레스가 담당합니다. 요청마다 회원 서비스를 호출하지 않으며, 서명만으로 판단합니다.  
템플릿에서는 게이트웨이에서 한 번, 각 서비스에서 또 한 번 회원 서비스를 동기 호출합니다. 이 방식은 회원 서비스의 응답 지연 시 전체 요청 처리 속도가 저하될 수 있습니다(16.3).
