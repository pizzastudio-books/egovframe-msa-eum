# 이음 — 서비스 분리본 (eum-services)

4~5부에서 쓰는 스냅숏입니다. 한 덩어리였던 이음을 네 벌로 나눈 뒤의 모습입니다.

| 모듈 | 담당 | 갈라져 나온 곳 |
| --- | --- | --- |
| `eum-gateway` | 토큰 검증 · 권한 전파 · 감사 로그 | 16장 |
| `eum-core` | 회원 · 공통 · 지원사업 · 신청 · 심사 | 본체로 남은 것 |
| `eum-notification` | 문자 · 메일 발송 | **첫 분리(15장)** |
| `eum-payment` | 지급 지시 · 이체 연계 · 야간 배치 | 17장, 사가는 18장 |
| `eum-contract` | 서비스 사이에 오가는 이벤트 규격 | — |

## 데이터베이스도 나뉘어 있습니다

| 서비스 | 데이터베이스 | 계정 | 인스턴스 |
| --- | --- | --- | --- |
| eum-core | `eum` | `eum_app` | 공용 |
| eum-notification | `eum_noti` | `noti_app` | 공용 |
| eum-payment | `eum_pay` | `pay_app` | **전용** |

계정 권한이 자기 데이터베이스로 묶여 있어, 알림이 신청서를 조회하려 하면 문법 오류가
아니라 **권한 오류**로 막힙니다. 경계가 코드에만 있는 것이 아니라 데이터에도 있습니다.

표준프레임워크 MSA 템플릿은 여기까지 가지 않습니다. 여섯 서비스가 계정 하나를 공유하고
그 계정에 모든 데이터베이스 전권이 있습니다. 그 차이를 13.2에서 다룹니다.

## 흐름

```
[본체]  심사 승인 저장 + 아웃박스 기록          ← 한 트랜잭션. 여기까지는 ACID
          │
        발송기가 아웃박스를 읽어 브로커로 발행
          │
[지급]  선정됨 수신 → 지급 지시 생성 → 야간에 금융망 이체
          │
     ┌────┴────┐
   성공        실패
     │          │
[본체]  지급완료됨 수신          지급실패됨 수신
      신청을 지급완료로           신청을 접수로 되돌림 (보상)
```

**아웃박스가 왜 필요한가.** 템플릿은 저장 직후 곧바로 발행합니다. 저장은 됐는데 발행
전에 프로세스가 죽으면 이벤트가 사라집니다. 아웃박스는 이벤트를 업무 자료와 같은
트랜잭션으로 적어 그 틈을 막습니다(18.1·18.2).

**멱등이 왜 필요한가.** 브로커는 한 번 이상 전달을 보장할 뿐 정확히 한 번을 보장하지
않습니다. 아웃박스 발송기도 실패하면 다시 보냅니다. 그래서 받는 쪽이 두 번 와도 결과가
같아야 합니다. 알림과 지급은 `event_id` 를 기록해, 본체는 상태를 보고 걸러 냅니다(18.4).

**브로커를 아는 코드는 어디인가.** 아웃박스 발송기와 리스너 어댑터, 두 곳뿐입니다.
업무 코드는 아웃박스에 적기만 합니다. RabbitMQ 를 카프카로 바꿔도 손댈 곳이 그 둘로
좁혀집니다(부록 F).

## 돌려 보기

```bash
./gradlew build          # 시험 84건
./gradlew :eum-core:bootRun          # 8080
./gradlew :eum-notification:bootRun  # 8081
./gradlew :eum-payment:bootRun       # 8082
./gradlew :eum-gateway:bootRun       # 8000
```

브로커와 DB 는 `../local/` 에 있습니다. 실습은 그쪽 안내를 따릅니다.

## 브로커 없이 검증합니다

시험은 RabbitMQ 를 띄우지 않습니다. Spring Cloud Stream 의 시험 바인더가 큐 대신
메시지를 넣고 뺍니다. 그래서 `./gradlew build` 만으로 리스너·멱등·아웃박스·보상까지
확인됩니다.

브로커를 실제로 띄워 붙이는 것은 별개의 확인이고, 그 절차는 `../local/` 에 있습니다.

## 게이트웨이를 MVC 로 만든 이유

Spring Cloud Gateway 는 리액티브가 기본이지만 `spring-cloud-starter-gateway-server-webmvc`
로 서블릿 위에서 돌릴 수 있습니다. 이 책은 리액티브를 쓰지 않기로 했으므로 예외를 두지
않았습니다. 그 판단은 16.2에 있습니다.

게이트웨이는 **토큰 검증·권한 전파·감사 로그**를 맡습니다. 경로 분배와 TLS 종단은 인그레스가
맡습니다. 그리고 요청마다 회원 서비스를 부르지 않습니다 — 서명만으로 판단합니다.
템플릿은 게이트웨이에서 한 번, 각 서비스에서 또 한 번 회원 서비스를 동기 호출하는데,
그러면 회원 서비스가 느려질 때 전부 느려집니다(16.3).
